# 루메뜨 프로젝트 현황 및 합의된 요구사항

기준일: 2026-10-28 (한국 시간)

이 문서는 지금까지 사용자와 합의한 업무 규칙, 실제 외부 응답에서 확인한 사실, 현재 코드 상태와 남은 작업을 정리한 인수인계 문서입니다. **확인한 사실과 구현 예정 사항은 구분합니다.** 다른 PC나 새 개발 세션에서도 이 문서부터 확인합니다.

## 1. 서비스 목적과 범위

루메뜨는 네이버 스마트스토어에 등록된 판매 상품을 기준으로 거래처 실버테라피 상품을 조회하고, 공급가·상품 정보·옵션·품절 및 판매 재개 변화를 감지하는 관리자 시스템입니다.

- 거래처 전체 상품을 수집하지 않습니다. 네이버에서 실제 조회된 내 판매 상품만 거래처 조회 대상으로 삼습니다.
- 상품 단위 매핑과 옵션 단위 매핑을 분리합니다.
- 공급처 가격과 스마트스토어 판매가는 별도 값입니다. 공급가 변경을 판매가에 자동 적용하지 않습니다.
- 네이버 상품 등록·가격 수정·판매 상태 변경은 현재 연동 검증 범위에 없습니다.
- 외부 API와 HTML 예시 또는 합성 테스트를 실제 연동 성공으로 보고하지 않습니다.

## 4. 네이버 커머스 API에서 확인한 사실

### 인증 및 보안

- 회사 PC의 API 호출 공인 IP를 사용자가 커머스API센터에 등록했습니다.
- 사용자가 루트 `.env.local`에 인증정보를 직접 설정했고, SELF 유형으로 실제 인증이 성공했습니다.
- 서버 간 Client Credentials 방식입니다. bcrypt + Base64 서명을 만들고 Bearer 토큰으로 호출합니다.
- `bcryptjs@3.0.3`과 `dotenv`를 API 패키지 의존성으로 추가했습니다. 별도 전역 패키지는 필요 없습니다.
- 시크릿·토큰·서명은 프론트엔드나 거래처 확장 프로그램에 전달하지 않습니다.
- 개인 Mac/배포 서버에서 호출할 때에는 해당 환경의 외부 요청 IP와 등록 허용 IP를 다시 확인해야 합니다.

### 조회 경로와 품번 원본

| 용도             | 공식 API                                          |
| ---------------- | ------------------------------------------------- |
| 토큰 발급        | POST /v1/oauth2/token                             |
| 상품 목록 조회   | POST /v1/products/search                          |
| 원상품 상세 조회 | GET /v2/products/origin-products/:originProductNo |

상품 목록 API의 POST는 상품 생성 요청이 아니라 조회 요청입니다.

실제 스토어 품번은 **`originProduct.detailAttribute.manufactureDefineNo`**에 있었습니다. 판매자 관리 코드와 `naverShoppingSearchInfo` 하위 값으로 잘못 가정하면 안 됩니다.

조합형 옵션은 `originProduct.detailAttribute.optionInfo.optionCombinations`에서 ID, 옵션 값, price, stockQuantity, usable을 확인했습니다. 옵션 그룹명도 함께 조회했습니다. 네이버 옵션 가격과 공급처 옵션 금액의 의미를 동일하게 가정하지 않습니다.

## 6. 상품 매핑 규칙 (사용자 확정)

현재 분류는 B=팔찌, R=반지, N=목걸이입니다.

1. 네이버에서 가져온 원본 품번에서 첫 글자와 마지막 5자리를 추출합니다.
2. 마지막 5자리로 거래처 검색을 수행합니다. 거래처 전체 목록은 수집하지 않습니다.
3. **정상 검색 응답인지 먼저 확인**합니다. 인증·HTTP·네트워크·파싱 문제가 있으면 실패로 종료하고 기존 상태와 가격을 유지합니다.
4. 검색 후보의 전체 it_id에서 첫 글자와 마지막 5자리가 모두 같은 상품만 남깁니다.
5. 최종 후보가 정확히 1개이면 연결하고 거래처 전체 it_id를 보존합니다.
6. 정상 검색이 확인됐는데 최종 후보가 0개이면 SOLD_OUT으로 판정합니다.
7. 최종 후보가 2개 이상이면 임의 선택하지 않고 매핑 오류로 기록합니다.
8. 품절 상품이 이후 정상 검색에서 유일하게 매핑되면 ACTIVE로 복구하고 변경 이력을 남깁니다.

등록 시기 코드가 다를 수 있으므로 품번 전체 문자열의 동일성을 요구하지 않습니다. 예: 실제 스토어 `R260115255`와 실제 거래처 `R230315255`는 `R` + `15255`로 일치합니다.

현재 스토어에는 E로 시작하는 상품도 있습니다. E는 현재 합의된 B/R/N 범위 밖이므로 **미지원 분류/확인 필요**로 처리하고 품절로 판정하지 않습니다. 지원 확대는 별도로 결정합니다.

## 7. 옵션 매핑 규칙 (사용자 확정)

**다른 상품에도 공통으로 적용할 업무 규칙: 네이버 상품에 사이즈 옵션만 있으면 Silver 상품입니다.** 이는 HTML에서 추측한 것이 아니라 사용자가 명시한 규칙입니다.

| 네이버 옵션 구성                 | 거래처 연결 규칙                             |
| -------------------------------- | -------------------------------------------- |
| 사이즈만 존재                    | Silver + 같은 사이즈                         |
| 색상과 사이즈 존재               | 색상과 사이즈 모두 일치                      |
| 일치하는 옵션이 없거나 복수 존재 | 임의 연결하지 않고 확인 필요                 |
| 옵션이 아예 없음                 | 사이즈 전용 Silver 규칙을 자동 적용하지 않음 |

상품 옵션 전체를 분석 대상으로 하며 특정 테스트 옵션 하나로 제한하지 않습니다. 다만 거래처에 존재하는 옵션 전체와 현재 네이버에서 판매 중인 옵션 범위는 별개입니다. 거래처 Gold/Rose Gold 옵션이 있다고 네이버에 자동 등록하거나 판매 대상으로 간주하지 않습니다.

사용자는 향후 색상·사이즈 전체 판매도 고려하고 있지만, 실제 네이버 등록 상태를 기준으로 매핑해야 합니다. 옵션 ID·바코드 원본을 보존하고 순번이나 색상 접두어로 바코드를 만들어내지 않습니다. 바코드가 바뀐 상황의 동일 옵션 판정 정책은 추가 설계가 필요합니다.

### B. 실제 판매 상품: R260115255 ↔ R230315255

- 네이버 원상품번호: 12871392673.
- 첫 글자 R 및 끝 5자리 15255가 일치합니다.
- 받은 자료는 거래처 상세입니다. `15255` 정상 검색의 최종 후보가 정확히 1개인지까지 종단 검증한 것은 아닙니다.
- 진단 팝업 SKU 입력에는 거래처 코드 R230315255가 들어 있었습니다. 운영 구현은 팝업 입력을 신뢰해 판매 품번으로 저장하지 않고 네이버 원본 R260115255를 사용해야 합니다.
- 현재 네이버 옵션은 size 9/11/13/15/17의 5개입니다. 사용자가 Silver 판매 상품이라고 확인했습니다.
- 거래처 옵션은 15개입니다. 바코드 15개는 해당 수집 안에서 고유했습니다.

| 거래처 색상 | 사이즈            | 옵션 금액  | 현재 네이버 연결                     |
| ----------- | ----------------- | ---------- | ------------------------------------ |
| Silver      | 9, 11, 13, 15, 17 | 각각 11000 | 같은 사이즈 5개에 연결하는 규칙 확정 |
| Gold        | 9, 11, 13, 15, 17 | 각각 14000 | 현재 연결하지 않음                   |
| Rose Gold   | 9, 11, 13, 15, 17 | 각각 14000 | 현재 연결하지 않음                   |

이 두 상품에서는 `itop_pay[]`에 추가금이 이미 포함됩니다. 예를 들어 14000에 화면의 +3000을 다시 더하지 않습니다. 다른 가격 구조의 상품은 검증 없이 일반화하지 않습니다.

### C. 빈 검색 결과

사용자가 로그인한 상태에서 보낸 `keyword=59999` 자료는 상품 링크 0개, 상품 필드 0개였습니다. SKU 입력란에 남아 있던 R221057427과 실제 검색어가 다르므로 해당 상품의 품절 증거가 아닙니다.

정상 빈 결과와 로그인 만료의 구별 표식은 아직 확인하지 못했습니다. **빈 결과 사례를 확보한 것과 안전한 자동 품절 판정이 완성된 것은 다릅니다.** 사용자는 나중에 로그인 만료 자료를 보내기로 했습니다.

## 9. 최종 DB 설계 요구사항

기존 샘플 초안을 무조건 유지하지 않습니다. 실제 연동 구조에 맞춰 다음을 재설계해야 합니다.

- StoreProduct: 네이버 원상품/채널 식별자, 원본 품번, 판매 상태와 옵션 정보.
- SupplierProduct: 거래처 전체 it_id, 기본 금액, 공급처 상태와 상품 정보.
- SupplierProductOption: 옵션명, 식별자 후보, 바코드, 옵션별 금액, 제공되는 경우 중량, 활성/제거 상태.
- ProductMapping: 상품 연결, 매핑 키, 옵션 연결 및 자동/확인 필요 상태.
- ProductChangeLog: 상품/옵션 변경 유형과 이전·새 값, 발생 시각, 동기화 실행 연결.
- SyncHistory: 실행 성공·실패, 대상/처리/변경 수, 안전한 오류 코드와 시작/완료 시각.

후속 구현에서 StoreProductOption과 OptionMapping까지 포함한 8개 모델을 작성했습니다. 네이버 옵션 식별자와 공급처 옵션 식별자를 별도 보존하며 `isSample` 필드는 사용하지 않습니다. DB 적용 승인 전이고 상세 내용은 SCHEMA-OPTION-MAPPING.md를 참고하세요.

- 금액은 Decimal 등 정확한 자료형으로 저장합니다. JSON 응답에서는 금액을 문자열로 전달합니다.
- 최초 수집은 기준값만 저장하고 변경 이력을 만들지 않습니다.
- 이후 상품명·기본가·옵션 금액/명칭/바코드/중량·옵션 추가/제거·품절/판매 재개를 비교합니다.
- 동일 값이면 불필요한 UPDATE와 변경 이력을 만들지 않습니다.
- 동시 실행과 반복 요청에도 중복 이력이 생기지 않도록 트랜잭션·잠금·유니크 제약을 설계합니다.
- 수집 실패를 옵션 제거/품절로 오인하지 않도록 스냅샷 완전성을 검증해야 합니다.
- DB 적용 전 새 SQL을 보여주고 승인받습니다. 기존 데이터 삭제·초기화·파괴적 마이그레이션은 금지입니다.
- 기존 `docs/MVP-MIGRATION.md`, 샘플 seed 및 샘플 통합 검증 스크립트는 이전 초안입니다. 새 설계 승인 없이 production에 실행하지 않습니다.

## 10. 진단 도구와 운영 서비스의 차이

### 지금 사용하는 개발용 도구

`사용자 Chrome → 진단 확장 → 127.0.0.1:43187 임시 수신기 → .diagnostics 파일 → 개발자가 분석`

- 실행: `pnpm inspect:supplier`.
- 진단 확장 폴더: `apps/supplier-inspector`.
- 수신기는 30분 후 종료하고 최대 20회 수신합니다. 꺼져 있으면 보내기가 실패합니다.
- 재시작하면 로컬 단기 연결키가 바뀝니다. 확장 팝업을 닫고 다시 열어야 합니다.
- 확장 코드를 업데이트한 경우 Chrome 확장 관리 화면에서 새로고침합니다.
- 모든 오류가 동일 문구로 보이는 현재 팝업은 분석 실패/전송 실패 원인을 충분히 구분하지 못합니다. 진단 UX 개선 과제입니다.

### 계획한 운영 흐름

`인증된 어드민의 동기화 버튼 → 확장 프로그램 → 로그인된 거래처 검색·상세 조회 → 인증된 기존 Fastify API → 검증·비교·Neon 저장`

- 사용자는 최초 확장 설치와 거래처 직접 로그인 후 어드민에서 동기화를 누릅니다.
- 사용자가 터미널로 서버를 실행하거나 로컬 JSON을 관리하게 만들지 않습니다.
- 진단 서버를 별도로 배포할 계획이 아닙니다. 기존 Fastify API에 작업 전달·상품 정보 수신 기능을 구현합니다.
- 관리자 인증, 확장 연결 인증, 작업 전달/결과 검증, 로그인 만료 재로그인 안내, 요청 제한 및 오류 처리는 아직 구현해야 합니다.
- 공급처 비밀번호·세션 쿠키·인증 토큰을 Fastify나 DB로 보내지 않습니다. 거래처 로그인 세션은 사용자 브라우저에만 둡니다.
- 기존 샘플 sync API 접근 제한은 운영 관리자 인증 완성을 의미하지 않습니다.

## 13. 다음 작업 순서와 승인 경계

1. 로그인 만료 자료를 받아 정상 0건과 인증 실패의 구별 기준을 정합니다.

4. **사용자 승인 후에만** DB 마이그레이션을 적용합니다.
5. 운영 관리자 인증 및 확장 프로그램 연결·동기화 API·Vue 화면을 연결합니다.

추가 유료 리소스나 DB 브랜치를 생성하지 않습니다. Git commit/push 및 클라우드 배포는 승인 없이 진행하지 않습니다. 새 설치 항목·환경변수·명령을 추가할 때 한국어 README와 관련 docs도 함께 업데이트합니다.
