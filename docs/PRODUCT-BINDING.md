# 실제 스마트스토어 상품 바인딩

작업일: 2026-10-29. 기존 production DB·pnpm workspace를 그대로 사용합니다. 신규 패키지, DB 마이그레이션, 추가 클라우드 리소스는 없습니다.

## 구현 범위

`네이버 API 읽기 → 정규화·전체 응답 검증 → DB 트랜잭션 저장 → Fastify 목록/상세 → Vue 조회`를 연결했습니다. 공급처 로그인이나 네이버 상품 수정 API는 호출하지 않습니다.

- 원상품 번호와 실제 `detailAttribute.manufactureDefineNo`를 보존합니다. 품번을 다른 임의 필드에서 추정하지 않습니다.
- 네이버 옵션 ID, 옵션 그룹 원문, 추가 판매가, 재고, 사용 여부를 저장합니다. 사이즈만 있는 옵션의 색상은 사용자 업무 규칙에 따라 Silver입니다.
- 옵션 없는 상품은 가상의 Silver 옵션을 만들지 않습니다. E 등 지원 외 품번도 판매 상품으로 저장하지만 공급처 매핑은 UNSUPPORTED로 표시합니다.
- 옵션 추가 판매가는 네이버 판매가 기준입니다. 공급처 공급가로 사용하지 않습니다.
- StoreProduct/StoreProductOption은 고유 키로 식별하고 값이 달라진 경우만 UPDATE합니다. Decimal 표현 및 JSON 객체 키 순서 차이로 UPDATE하지 않습니다.
- 전체 목록/모든 상세 정규화가 완료된 뒤 저장합니다. 인증·네트워크·검증 오류에서는 상품 변경을 시작하지 않습니다. 저장 실패는 전체 트랜잭션을 롤백합니다.
- 현재 안전 상한은 자기 스토어 상품 100개입니다. 전체 응답이 100개를 넘거나 목록이 불완전하면 부분 저장하지 않고 중단합니다. 상세 요청은 순차 처리하고 기본 600ms 간격을 둡니다.
- 기존 옵션이 있는데 상세 응답의 조합형 옵션 목록이 누락되면 전체 저장을 중단합니다. 명시적으로 완전한 목록이 확인될 때만 사라진 옵션을 active=false로 변경하며 삭제하지 않습니다.
- 품번·옵션 정의가 바뀌면 기존 연결은 확인 필요로 변경합니다. 공급처 상태/공급가를 추정해 덮어쓰지 않습니다.
- 실행 이력은 NAVER/SUCCESS 또는 FAILED로 기록합니다. 같은 요청 키 재실행은 실행 이력까지 중복 생성하지 않습니다. dry-run은 DB에 실행 이력도 쓰지 않습니다.

## Windows/macOS 공통 실행

서버용 기존 네이버·Neon 환경변수는 루트 `.env.local`에 보관합니다. `.env.example`의 `NAVER_STORE_KEY=lumette`는 비밀값이 아닌 DB 구분 키이며 기본값도 lumette입니다. 최초 저장 후 이 키를 임의로 바꾸면 같은 스토어를 다른 대상으로 저장할 수 있으므로 변경하지 마세요.

```sh
pnpm install --frozen-lockfile
pnpm naver:import          # 실제 네이버 읽기 및 정규화 미리보기, DB 쓰기 없음
pnpm naver:import --apply  # 실제 DB 저장. 작업할 스토어·대상을 확인하고 실행
pnpm dev
```

`http://localhost:5173`의 상품 관리 탭에서 상품을 클릭하면 스마트스토어 옵션·추가 판매가·재고를 조회합니다. 공급처 연동 상태는 별도로 표시합니다. 데이터가 이미 화면에 로드되어 있으면 새로고침 버튼을 누르세요.

수입 작업은 현재 서버용 CLI로만 실행합니다. 공개 쓰기 API나 프론트엔드 내 서버 토큰을 추가하지 않았습니다. 관리자 인증이 완성되기 전에는 API를 공개 배포하지 마세요. 다른 PC에서는 새 공인 IP의 네이버 API 허용 여부도 확인해야 합니다.

## 실제 검증 결과

- 실제 네이버 신규 조회: 판매 상품 8개, 조합형 옵션 16개, 공급처 지원 외 품번 1개.
- 최초 저장: productsCreated=8, optionsCreated=16, UPDATE/비활성화 0건.
- 실제 네이버 재조회 후 재수입: 상품·옵션 생성/UPDATE/비활성화 모두 0건, updatedAt 유지.
- 같은 requestKey 재실행: 상품·옵션뿐 아니라 실행 이력도 중복 없음. 정상 실행 이력은 최초 저장과 재수입의 2건입니다.
- 실제 DB 조회 API에서 목록 8개, 상세 8개와 옵션 16개, 대시보드 8개를 확인했습니다. 최초 바인딩으로 공급처 변경 이력은 생성하지 않아 0건입니다.
- 기존 공급처 연결을 임의로 생성하지 않았습니다. 공급처 옵션 미리보기는 ACTIVE_PRODUCT_MAPPING_REQUIRED로 확인 필요를 반환합니다.
- UI 옵션 표시 코드를 추가하고 전체 빌드를 검증했습니다. 브라우저 자동화용 연결은 사용할 수 없어 실제 브라우저 DOM/클릭 검증은 미완료입니다.
- 실행 중인 실제 HTTP API의 목록·상세·대시보드·변경 이력 응답, Vue 개발 서버 진입 페이지와 CORS 확인도 통과했습니다.
- `pnpm test` 전체 40개 통과, `pnpm build`·lint·포맷 검사 성공, Git 대상 민감정보 검사 통과. Vite 번들 크기 경고는 기존대로 남아 있습니다.

## 추가 검증 명령

먼저 `pnpm build`를 실행하세요.

```sh
node scripts/verify-products-readonly.mjs
node scripts/verify-bound-products.mjs
node scripts/verify-bound-products.mjs --http
node scripts/verify-import-idempotency.mjs
pnpm test
pnpm security:check
```

`--http`는 이미 실행 중인 localhost:3000 API와 localhost:5173 Vite 진입 페이지 및 CORS를 확인합니다. 브라우저 DOM 검증을 대체하지 않습니다.

`verify-import-idempotency`는 네이버를 실제 재조회하고 재수입하므로 **읽기 전용이 아닙니다**. 데이터가 동일하면 상품/옵션을 수정하지 않고 정상 실행 이력 1건만 추가합니다. 외부 상품이 바뀌었으면 실제 수정이 발생하고 0 UPDATE 검증은 실패할 수 있습니다. 최초 수입 후 대상과 데이터 상태를 확인하고 실행하세요.

실제 가격·재고는 변할 수 있으므로 위 숫자는 작업 시점 기록입니다. 초기 빈 DB였던 마이그레이션 보고서와 구분해 읽으세요.

## 다음 단계

실버테라피 정상 검색과 로그인 만료 구별, 옵션 ID 영속성을 더 확인한 뒤 공급처 기준 데이터 및 실제 매핑을 저장해야 합니다. 공급처 수집 없이 검색 미검증 상품을 품절로 만들지 않습니다. 상품이 관리자 화면에 표시되는 것과 공급처 연결·자동 변경 감지가 완성된 것은 다릅니다.
